# ITCodeX 元数据模块 - 总体架构设计

> 版本: v1.3
> 日期: 2026-09-06
> 技术栈: GoFrame v2 + MySQL 8 + CEL-Go + Yaegi
> 范围说明见 [设计方案总览](./README.md#对标-nocobase-的范围)
> GoFrame 边界见 [README · GoFrame 使用边界](./README.md#goframe-使用边界)

## 1. 设计目标

### 1.1 核心目标
- 提供类 NocoBase 的动态元数据管理能力（**裁剪后的子集**，不是完整 NocoBase）
- 支持运行时动态创建/修改/删除**普通表**和字段
- 按阶段交付字段 Interface（文本、数字、日期、选择、关系等）
- 支持单字段和多字段联合校验（CEL-Go）
- 支持通过 Yaegi 进行二次开发，无需重新编译
- 本机 Docker 部署 MySQL 8，开发环境统一、数据持久化

### 1.2 非功能目标
- 高性能：元数据缓存 + MySQL 连接池访问
- 持久化：MySQL InnoDB 事务
- 易扩展：插件化字段类型、校验规则、操作符
- 易二开：Yaegi 脚本热加载，支持业务逻辑定制

### 1.3 本模块边界
- **在范围内**：主库建模、HTTP CRUD、Filter 子集、CEL、Yaegi
- **不在范围内**：页面区块、权限、工作流、视图/SQL/继承/外部表、多数据库方言、Umzug 迁移框架
- **延后**：关系查询与写入（三期）、特殊表类型与公式/加密/几何（五期）

## 2. 技术选型

| 组件 | 技术选择 | 说明 |
|------|----------|------|
| Web框架 | GoFrame v2 | HTTP、中间件、配置、OpenAPI；系统表走 DAO，**不**把动态业务表交给 ORM |
| 数据库 | MySQL 8 | Docker 本机部署，账号 root / 123456，库名 itcodex |
| 系统表访问 | gdb + dao/do | 仅 `collections` / `fields` / `indexes` / `yaegi_scripts` |
| 业务表访问 | database/sql | 运行时 DDL，无法 `gf gen dao` |
| 校验引擎 | cel-go | 业务记录的单字段/多字段联合校验 |
| 脚本引擎 | Yaegi | Go 语言解释器，支持运行时动态执行 Go 代码，用于二开 |
| 主键生成 | Snowflake / UUID / NanoID | 支持多种主键策略 |
| JSON处理 | encoding/json + gjson | 高效 JSON 处理 |

## 3. 整体架构分层

```
API 定义 (api/*/v1 + g.Meta)
  静态 Meta：Bind + OpenAPI
  动态 CRUD：显式路由
  Yaegi 自定义：/api/custom/* 通配
        |
        v
Controller (ctx, req) -> (res, err)
  MiddlewareHandlerResponse / CORS / 上下文注入
        |
        v
internal/service（不用 logic/）
  Collection / Field / CEL / Yaegi / Repository
        |
        +-- 内存模型：Database / Collection / Field（不可 codegen）
        +-- 系统表：entity / do（gf gen dao，禁止手改）
        |
        v
数据访问
  系统表：g.DB() + dao/do
  业务表：database/sql + 动态 DDL
        |
        v
扩展：字段类型 / 操作符 / Yaegi 沙箱
```

## 4. 核心模块职责

### 4.1 Database 模块
- 通过 GoFrame `g.DB()` 管理默认 MySQL 连接；系统表 CRUD 走 `dao` / `do`
- 业务表连接可复用同一 `*sql.DB`（`g.DB().GetCore().DB`）或独立 `database/sql`，动态 DDL 不走 DAO
- 维护 Collection 和 Field **内存**注册表
- 启动时同步系统表与业务表结构（`CREATE`/`ALTER`），**不做**独立迁移框架
- 注册自定义字段类型、操作符、Repository
- 生命周期钩子仅服务 CEL / Yaegi，不实现 NocoBase JS 事件总线
- **不使用 `logic/` 目录**；上述能力实现于 `internal/service/metadata`

### 4.2 Collection 模块
- 描述数据表元信息（名称、字段、索引、类型等）
- 管理字段的增删改查
- 同步表结构到 MySQL
- 提供 Repository 实例
- **一期只实现普通表**；树/日历/评论/文件表仅保留类型枚举与 options，行为见第五阶段

### 4.3 Field 模块
- 描述字段元信息（名称、Interface、存储类型、校验规则）
- Interface 与存储类型分离，默认映射见 `02`/`05`
- 基础/选择/媒体按阶段注册；关系字段第三阶段；几何/公式/加密第五阶段
- 字段类型映射到 MySQL 数据类型

### 4.4 Repository 模块
- 提供统一的**业务表**数据 CRUD 接口（`database/sql`，不用 DAO/DO）
- 支持已声明的 Filter 子集（见 [05](./05-API接口设计.md#filter-操作符分期)）
- 支持排序、分页、`fields`/`except`
- `appends` 与关联写入：第三阶段
- **写入默认一个工作单元事务**：Create / Update / Destroy（含关联写入）自动 `Begin`；`*sql.Tx` 放入 `context`，全程共用
- 显式 `Repository.Transaction`：嵌套时加入已有事务，不新开连接
- Yaegi 钩子（beforeCreate/afterCreate 等）通过同一 `context` 访问 Repository，写当前库视为同一事务

### 4.5 Validation 模块（CEL-Go）
- HTTP 请求参数校验用 GoFrame `v:` 标签（见 `05`），不在本模块重复
- 单字段校验：必填、长度、范围、格式、正则等
- 多字段联合校验：跨字段表达式校验
- 自定义校验函数注册
- 编译后的 CEL 程序缓存
- 校验错误信息国际化

### 4.6 Yaegi 模块
- Go 脚本解释器初始化和管理
- 脚本沙箱环境（导出安全的 API）
- 脚本热加载和缓存
- 内置 CRUD 钩子点（before/after create/update/delete）
- 自定义 API 路由注册
- 脚本错误处理和日志

## 5. 元数据表结构（系统表）

系统自身使用以下元数据表存储配置。表结构稳定后由 `gf gen dao` 生成 `internal/dao`、`internal/model/do`、`internal/model/entity`，**禁止手改生成文件**。`created_at` / `updated_at` 由 GoFrame ORM 自动维护，业务代码不要手动赋值。可选增加 `deleted_at` 以启用软删。

这些表在系统启动时自动创建（或用 `manifest/sql` 初始化）：

### 5.1 collections - 数据表定义表
| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键(Snowflake) |
| name | varchar(255) | 表标识名，唯一 |
| display_name | varchar(255) | 显示名称 |
| table_name | varchar(255) | 数据库实际表名 |

| updated_at | datetime | 更新时间（ORM 自动维护） |

## 6. 启动流程

```
1. 加载配置（manifest/config + g.Cfg）
   └─ database.default.link / metadata.*

2. 连接 MySQL（g.DB 默认分组）
   ├─ Docker MySQL（localhost:3306 / itcodex）
   └─ 连接池由 GoFrame database 配置管理

3. 同步系统元数据表（dao 对应的固定表）
   ├─ 创建 collections 表
   ├─ 创建 fields 表
   ├─ 创建 indexes 表
   └─ 创建 yaegi_scripts 表

4. 注册内置字段类型（按阶段扩展）
   ├─ 一期：string/text/integer/bigInt/float/double/boolean/datetime
   ├─ 二期：选择/媒体/日期细分 Interface
   ├─ 三期：belongsTo/hasOne/hasMany/belongsToMany
   └─ 五期：uuid/nanoid/json/encrypt/formula/sort/sequence/几何

5. 注册内置查询操作符（一期子集）
   ├─ 比较：$eq/$ne/$gt/$gte/$lt/$lte/$in/$notIn/$between/$notBetween
   ├─ 逻辑：$and/$or/$not
   ├─ 空值：$isNull/$notNull
   └─ 字符串：$like/$notLike/$startsWith/$endsWith

6. 加载元数据到内存（系统表用 dao.Scan → 内存 Collection）
   ├─ 从 collections 表加载所有表定义
   ├─ 从 fields 表加载所有字段定义
   └─ 在内存中构建 Collection 和 Field 对象

7. 同步业务表结构
   └─ 根据元数据同步 MySQL 中的业务表

8. 初始化 Yaegi 脚本引擎
   ├─ 加载启用的 Yaegi 脚本
   ├─ 编译脚本并缓存
   └─ 注册自定义 API 路由

9. 启动 HTTP 服务（internal/cmd + gcmd）
   ├─ MiddlewareHandlerResponse / CORS / 元数据上下文
   ├─ Bind 静态 Meta Controller（g.Meta）
   ├─ 注册动态 CRUD 显式路由
   └─ 注册 Yaegi 自定义 API 通配路由
```

## 7. 关键设计原则

### 7.1 元数据缓存
- Collection 和 Field 定义在启动时加载到内存
- 元数据变更时同步更新缓存和数据库
- 提供缓存失效和刷新机制

### 7.2 生命周期钩子
- 校验与 CRUD：before/after validate/create/update/destroy，以及 **afterCommit**（仅提交成功后）
- Yaegi 脚本通过钩子点介入；不实现独立的全局事件总线产品
- `createdBy`/`updatedBy` 从请求上下文读取，无用户体系时留空
- 钩子内通过沙箱 Repository 改**当前 MySQL 业务表**时，必须走工作单元事务；失败回滚主表、关联与钩子写库。细则见 [04 · 工作单元](./04-Yaegi二开设计.md#43-crud-工作单元事务)

### 7.3 安全沙箱
- Yaegi 脚本运行在沙箱环境中
- 只暴露安全的 API 给脚本
- 脚本执行超时控制
- 资源使用限制（内存、CPU）

### 7.4 扩展性
- 字段类型可通过 RegisterFieldType 扩展
- 查询操作符可通过 RegisterOperator 扩展
- Repository 可自定义扩展
- CEL 自定义函数可注册

### 7.5 写入原子性
- 查询（Find/Count）不开写事务
- 单条写入 API 默认包事务；调用方不必再包一层
- Yaegi 禁止在 CRUD 钩子里做 DDL（MySQL DDL 会隐式提交，拆掉工作单元）
- HTTP / 邮件等副作用只允许 `afterCommit`，不允许 `afterCreate` 默认路径发送（避免回滚后通知已发出）
